# Исправление накопления Yggdrasil SLAAC-адресов

## Наблюдавшийся симптом

После возвращения устройств в домашнюю сеть страница LuCI `Status → Yggdrasil`
показывала для некоторых клиентов много адресов из делегированного роутером
Yggdrasil `/64`: у OnePlus 13 было видно 14 адресов, у POCO X3 — 31.

Это выглядело так, будто OpenWrt повторно выдаёт клиентам новые адреса. На самом
деле роутер анонсировал ровно один префикс, а список состоял преимущественно из
старых privacy IID, накопившихся в IPv6 neighbor cache после ротации адресов на
клиентах.

## Причина

В версии v4 серверная часть страницы статуса:

1. читала все записи `ip -6 neigh` для MAC-адреса клиента;
2. выводила каждую найденную запись как отдельный SLAAC-адрес;
3. при каждом обновлении страницы проверяла доступность каждого такого адреса.

Последний пункт создавал обратную связь: опрос исторического privacy-адреса мог
обновлять его NDP-состояние и мешать записи исчезнуть естественным образом.

Это не было ошибкой RA или выдачей нескольких префиксов. При SLAAC клиент сам
выбирает IID и вправе одновременно иметь стабильный и временные privacy-адреса.
RA не содержит механизма, который безопасно ограничивает каждый клиент ровно
одним адресом. Поэтому конфигурация `odhcpd`, DHCPv6, firewall и маршрутизация
Yggdrasil не менялись.

## Исправление в v5

В [RPC-бэкенде](source/yggdrasil-status-v5/root/usr/libexec/rpcd/luci.yggdrasil-status)
реализован выбор адреса по принципу stable-first:

1. Если для устройства закреплён канонический адрес в `config domain`, LuCI
   показывает и проверяет только его.
2. Иначе из MAC вычисляется стандартный modified EUI-64. Если этот адрес есть в
   NDP, показывается и проверяется только он.
3. Только для privacy-only устройств, у которых стабильный адрес определить
   нельзя, остаётся вывод фактически наблюдаемых адресов. Это необходимо, в
   частности, для iPhone, где несколько адресов являются нормальным поведением.

Таким образом, v5 не назначает и не удаляет адреса на клиентах. Она прекращает
показывать и активно опрашивать исторические privacy IID, когда доступен
стабильный адрес. Старые записи после этого удаляются из neighbor cache по
обычным тайм-аутам ядра.

## Отдельно о полноценных Yggdrasil-узлах

ThinkPad и OnePlus 13 запускают собственные клиенты Yggdrasil и являются
полноценными участниками overlay-сети. У каждого из них корректно существуют два
разных вида адресов:

- собственный адрес узла Yggdrasil на TUN-интерфейсе;
- SLAAC-адрес из маршрутизируемого LAN-префикса роутера.

Список Yggdrasil peers отвечает за первый адрес, а таблица LAN-клиентов — только
за второй. Флаг `router` в NDP у такого устройства объясняется включённым IPv6
forwarding и не создаёт дополнительную Yggdrasil-идентичность.

## Проверка результата

- Логика проверена на BusyBox-совместимых фикстурах и на реальном роутере.
- После установки v5 затронутые устройства отображались одной строкой со
  стабильным LAN SLAAC-адресом и сохраняли статус online.
- У OnePlus 13 число наблюдаемых на роутере NDP-адресов без принудительной
  очистки уменьшилось с 14 до 2, тогда как LuCI корректно продолжала показывать
  один стабильный адрес.
- Единственный `/64`, RA, Yggdrasil routing, firewall и DNS остались без
  изменений; при установке перезапускался только `rpcd`.
- Установочный архив v5 имеет SHA-256
  `26063dd0d0b89599e8123a6a67350b6d2606336c2080010e6474eef4358679a4`.

Изменение выпущено коммитом `1f9360c`; уточнение модели адресов полноценных
Yggdrasil-узлов — коммитом `11d3e19`. Общая архитектура описана в
[README](README.md), а регрессионные проверки — в [TEST_PLAN](TEST_PLAN.md).
